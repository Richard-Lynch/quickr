1. **[P1] A tile can show an enabled Start before its existing run has loaded** — [HomeModel.swift](/Users/richie/code/quickr-worktrees/t2-m2-race/ios/QuickrKit/Sources/QuickrData/Home/HomeModel.swift:150), [TopicTile.swift](/Users/richie/code/quickr-worktrees/t2-m2-race/ios/App/Home/Tiles/TopicTile.swift:116). Topic and run observations start independently. The first topics result sets `loaded`, making Home ready, while `runs` can still be empty. For a topic with an existing open run, the tile therefore briefly shows enabled Start. A tap finds the existing run in the database and returns it without enqueueing a start, but the tile does not navigate to it; it only increments its haptic counter. The later run observation may make the card appear, so the user’s Start intent is effectively lost. Gate the idle control on the initial run snapshot, or handle the existing-run result explicitly. The new tests use a fresh topic with no existing run and cannot detect this.

2. **[P1] The UI test does not deterministically exercise a launch rebind** — [RunUITests.swift](/Users/richie/code/quickr-worktrees/t2-m2-race/ios/UITests/RunUITests.swift:175). Holding subsequent feed requests does not hold `AppSession` at the forced rebind: the initial connect consumes its prefetched page, and the later pull can begin after connect and rebind have completed. The test also never asserts that a later request has arrived or is held before tapping. `waitForExistence` and XCTest’s tap synchronization leave the actual tap time uncontrolled. Thus the test can pass even if a tap during the rebind is lost. Add an observable barrier at the relevant bind transition, assert it is reached while Start is enabled, tap, and release it.

3. **[P2] The host test does not reproduce the launch path or the app’s action wiring** — [AppSessionTests.swift](/Users/richie/code/quickr-worktrees/t2-m2-race/ios/QuickrKit/Tests/QuickrDataTests/Session/AppSessionTests.swift:553). It waits for `session.start` to finish, then reconnects an already established session and constructs a separate `RunActions` directly. This verifies a same-store write while a particular forced bind is held, but bypasses the first registry-driven bind, Home’s independent observations, the tile’s task, and `AppEnvironment`’s writer wrapper. It would still pass for a race in any of those launch or UI steps. Exercise the actual first `start` with barriers around the registry bind and forced rebind, and cover the real tile/action path separately.

4. **[P2] The host test can pass even if the replacement scheduler never delivers the Start** — [AppSessionTests.swift](/Users/richie/code/quickr-worktrees/t2-m2-race/ios/QuickrKit/Tests/QuickrDataTests/Session/AppSessionTests.swift:563). `startRun` requests a flush from the *old* scheduler while the new bind is gated. The final assertion only checks whether a POST was recorded at any time, so that old scheduler can send it before the gate opens. The queued-item check does not prove delivery happened after the swap either. Hold or retire the old sender, assert no POST before releasing the bind, then verify the new scheduler sends and acknowledges the item.

5. **[P2] The fake-server hold is not atomic with admitting the first feed** — [UITestLaunch.swift](/Users/richie/code/quickr-worktrees/t2-m2-race/ios/App/Debug/UITestLaunch.swift:590). Each request checks `holdFeed` before the first request’s deferred `feedAnswered()` enables it. Concurrent feed requests can both pass that check and both be answered, contrary to the launch argument’s stated contract. Select and mark the first request under the same lock used to decide whether subsequent requests wait.

The conclusion that there is **no app race** is therefore not established. The same-store rebind code retains the old store and outbox until publishing the replacements, and requests a flush afterward, so the host test provides evidence for that particular swap. It does not rule out the visible Start window caused by independently loaded run state or prove that the reported dropped tap occurred in that swap.

## Resolution (m2-start-race, round 1)

1. **[P1] Start before the runs load: fixed** (846b70e7). This is a real launch race, though not the one #239 hit (R9's topic has no run at launch). `HomeModel.loaded` now needs the first topics *and* the first runs. A failed runs observation still lets the list show. New host test `HomeModelTests.theListWaitsForTheRuns` holds the runs back with a new `localRunsForTesting` seam. With the old `loaded = true`, it fails at `!model.loaded` and `phase == .loading` (mutation run).
2. **[P1] The UI test doesn't hold the forced rebind: stands, covered by the host test.** Whether the tiles can show before the connect's forced rebind depends on whether the registry-change listener's rebind lands first. Both orders were logged in instrumented runs: diag-1 shows the forced bind first and the tiles after it; diag-2 shows the listener bind first, then the tiles, then the forced bind 90 ms later. A UI test can't pin that order. `AppSessionTests.aStartDuringTheLaunchRebindIsKept` holds the forced rebind at `beforeBindForTesting` and starts a run inside the hold, so it is deterministic. The UI test pins what it can: the next pull is in flight at the tap. The instrumented diag-2 run logged the held feed request 0 ms after the topics appeared and 2.4 s before the tap.
3. **[P2] The host test bypasses the launch and the UI wiring: partly stands.** The UI test drives the app's own path: `AppEnvironment`'s writer wrapper, the tile's action and Home's observations. The host test isolates the one window the UI test cannot pin, which is item 2. HomeModel's independent observations are now covered by item 1's test.
4. **[P2] The POST may come from the old scheduler: accepted as intended.** The claim is "not dropped", not "sent by the new scheduler". The doc comment now says the start is sent by the old scheduler or by the new one's first flush. The test proves the item is queued at once in the bound store and is sent.
5. **[P2] The hold isn't atomic: fixed.** `waitIfFeedHeld` admits the first request and turns `holdFeed` on inside the same lock. The deferred `feedAnswered()` is gone.

## Round 2

Codex r2 (re-review of 846b70e7..c59cb816):

> 1. **[P1] A failed runs observation restores the unsafe Start state** — HomeModel.swift:207. If the initial runs read fails independently of the topics read, this marks runs as read and shows the list with an empty `runs` dictionary. An existing open or finishing run can then appear as an idle topic with an enabled Start button—the race this change is meant to prevent. The runs observation has also ended, so it cannot later correct the tile, and the user receives no error or retry action. Surface the failure and allow retry instead of treating it as a successful empty snapshot.

**Resolution: fixed.** If the runs observation fails before its first value, the list stays back. The error is kept as `loadError`, and the topics' later emissions keep it set instead of clearing it. Home then shows its error banner with Retry, and the phase is `.failed` while nothing is loaded. Retry restarts `observe()`. `theListWaitsForTheRuns` now checks the failure (`phase == .failed`, not loaded) and the retry that reads the runs.
