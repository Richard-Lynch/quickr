**Findings**

1. **[P1] Optimistic entry creation does not update `last_entry`.** [outboxEffects.ts](/Users/richie/code/quickr-worktrees/t2-m4-fsummary/frontend/src/api/outboxEffects.ts:72) updates the cached entry count, but does not patch `last_entry` from the queued payload. Section 2 requires that patch on enqueue. An offline quick log therefore leaves the tile showing the previous entry until the outbox is acknowledged and the list can refetch. Patch the cached topic’s `last_entry` when enqueueing, account for ordering by `captured_at`, and restore it on rollback. Add an offline enqueue and rollback test.

2. **[P1] The staleness test verifies the cache, not the tile’s displayed entry.** [lastEntry.staleness.test.tsx](/Users/richie/code/quickr-worktrees/t2-m4-fsummary/frontend/src/api/lastEntry.staleness.test.tsx:112) asserts only that `listTopics` contains a new ID. [TopicTile.tsx](/Users/richie/code/quickr-worktrees/t2-m4-fsummary/frontend/src/components/topics/TopicTile.tsx:91) still reads a separate `lastEntryOptions` query with a five-minute stale time and does not consume `last_entry` or `TopicSummaryLine`. A remote change can consequently reach the list cache while the visible quick-log answer remains old. The plan assigns that integration to T2-WIRE, so this is an outstanding integration dependency rather than a file-ownership violation by this branch. Add the §7 tile test at that seam: render the tile, change the remote entry, and assert the visible summary updates within the bound and that the extra entry/version queries are gone.

3. **[P2] Focus coverage does not exercise production’s freshness policy.** [lastEntry.staleness.test.tsx](/Users/richie/code/quickr-worktrees/t2-m4-fsummary/frontend/src/api/lastEntry.staleness.test.tsx:137) explicitly uses a harness in which the query is stale immediately. Production uses a 20-second `staleTime` in [queryClient.ts](/Users/richie/code/quickr-worktrees/t2-m4-fsummary/frontend/src/api/queryClient.ts:22), so a focus shortly after a fetch will not necessarily refetch. Use the production query configuration in the test and cover a remote edit followed by focus while the cache is fresh. If §2’s “at the next focus” is intended literally, configure focus refetch to run even for fresh data.

The new summary port otherwise follows the reference for the cases reviewed. I found no demonstrated shared-file or ownership violation in the diff; the plan explicitly reserves the tile wiring for T2-WIRE. I did not run the test suite.
