**Findings**

1. **[P2] The default topic listing can exceed the one-extra-query bound.** In [topics.py](/Users/richie/code/quickr-worktrees/t2-m4-lastentry/backend/app/services/topics.py:166), the `selectin` relationship loads answers for every row passed to `_summaries`. For the default `sort=due`, [list_topics](/Users/richie/code/quickr-worktrees/t2-m4-lastentry/backend/app/services/topics.py:282) passes the entire matching topic set before slicing the requested page. SQLAlchemy batches select-in loads, so more than 500 topics can produce multiple answer queries for one page; it also loads answers for topics absent from that page. Compute due ordering first, then load `last_entry` answers for the selected page in one query. Add a test with more than 500 matching topics and a small page.

2. **[P2] Shared-file edits do not follow the plan’s delimiter rule.** [api.py](/Users/richie/code/quickr-worktrees/t2-m4-lastentry/backend/app/schemas/api.py:1223) changes the feed docstring outside the M4 block. In [topics.py](/Users/richie/code/quickr-worktrees/t2-m4-lastentry/backend/app/services/topics.py:166), the changed unpacking has an inline marker rather than a delimited block. The additions also use multiple M4 blocks in files for which the plan calls for at most one block per milestone; `_summaries` and `_base_select` are specifically shared with M3. Consolidate the additions into the permitted blocks, and route edits that cannot fit through the owning lead for integration.

3. **[P2] The home-vector shape change needs the prescribed ownership and stack treatment.** [home-vectors.json](/Users/richie/code/quickr-worktrees/t2-m4-lastentry/shared/fixtures/home-vectors.json:1) now has a new field on every topic. The stated amendment authorizes that shape and preserves the cases, but [the plan](/Users/richie/code/quickr-worktrees/t2-m4-lastentry/docs/specs/t2-plan.md:205) still requires existing vector shape changes to go through the vector owner and form a stack with affected consumers. Land or document the owner-coordinated stack, with its consumer checks, or have the lead explicitly amend that process for this vector.

4. **[P2] The iOS DTO change touches an M3-owned file without an indicated owner handoff.** [TopicDTO.swift](/Users/richie/code/quickr-worktrees/t2-m4-lastentry/ios/QuickrKit/Sources/QuickrData/Contracts/TopicDTO.swift:45) implements the requested decode-only `@RequiredKey` amendment correctly in intent, but the ownership table assigns this file to M3 and requires other milestones to send patches to the owner’s lead. Have that owner land the patch or record the agreed ownership exception. The same file also contains multiple M4 delimiters, which should be reconciled with the shared-file rule where applicable.

5. **[P3] The feed test does not prove that entry creation does not resend a topic.** [test_api_topics.py](/Users/richie/code/quickr-worktrees/t2-m4-lastentry/backend/tests/test_api_topics.py:394) takes its cursor after the creates. Its tail assertion covers the later update and deletes, but a topic change emitted by creation would already be before the cursor. Capture a cursor before creation and assert that create, update, and delete each produce their expected entry changes without a topic item.

The amended requirements explain the `lastEntry` DTO fields and the added home-vector fields; I did not treat those changes themselves as spec drift. I reviewed the diff statically and did not run tests or verify generated-file regeneration.
