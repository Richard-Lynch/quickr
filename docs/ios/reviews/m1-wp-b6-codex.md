# Codex review: M1 WP B6 (round 1)

**REQUEST CHANGES**

- **Major — APNs closes before the scheduler stops.** `backend/app/main.py:31` orders `scheduler.lifespan` before `apns.lifespan`; combined context managers unwind in reverse order. Shutdown therefore closes clients and clears `_Holder` while a tick can still be sending. A concurrent send can fail against a closing client or create another client after cleanup, leaking it. **Fix:** enter the APNs lifespan before the scheduler lifespan, so scheduler cancellation and cleanup finish first. Add an application-level shutdown test with a suspended APNs request; the isolated sender-close test misses this interaction.

- **Major — the 30-second tick budget does not bound delivery.** `backend/app/services/scheduler.py:78` checks the deadline only between topics. One topic with many targets can spend minutes inside `send_to_all`; HTTPX’s timeout bounds individual network operations, not the whole fan-out. Meanwhile, bookkeeping flushed after earlier topics holds target row locks until commit, potentially blocking registration or a manual test holding the feed lock. **Fix:** enforce an elapsed-time deadline around delivery, explicitly retaining send-then-mark semantics on cancellation. Add a test with delayed async transport responses and multiple semaphore batches. `backend/tests/test_apns.py:551` merely sets a negative budget and verifies the between-topic check.

- **Major — device tokens reach diagnostic logs.** `backend/scripts/apns_send.py:52` enables INFO logging globally, which enables HTTPX request logs containing `/3/device/{token}`. Additionally, `backend/app/services/push/apns.py:258` retains transport exception text and chaining, and `backend/app/services/push/__init__.py:128` logs the resulting traceback; URL-bearing HTTPX exceptions can therefore expose tokens through failure logging. **Fix:** suppress or redact HTTPX request logging for this client and log sanitized transport failures without URL-bearing exception chains. Add log-capture tests covering successful script delivery and a URL-bearing transport failure.

- **Minor — incomplete sandbox overrides silently fall back to the production key.** `backend/app/services/push/apns.py:116` accepts a sandbox key ID without its PEM, or PEM without its ID, then uses `sandbox or key`. For an environment-restricted production key this creates a configuration that appears enabled but consistently fails sandbox delivery. **Fix:** detect any partially supplied sandbox override and report an explicit configuration error; only inherit the default key when no override fields are supplied. Cover both partial combinations.

The remaining core implementation looks consistent with B6: synchronous lazy-client creation and JWT mutation avoid task interleaving before an await; caching uses 50 minutes, with a guarded one-time expired-token retry; payload size is measured after UTF-8 serialization; environment routing and migration constraints match the model. Error handling correctly includes Apple’s **413** `PayloadTooLarge`, despite the research table’s 400 entry. [Apple response reference](https://developer.apple.com/documentation/usernotifications/handling-notification-responses-from-apns)

Registration uses `ExpectIdentity` plus `@writer`; manual sends use `@writer_once`; the scheduler does not acquire the feed advisory lock. Web Push rendering preserves the existing payload shape and serialization. Missing actionable fields, including `server_id`, are explicitly deferred to B7.

Review was static; tests were inspected but not executed.
