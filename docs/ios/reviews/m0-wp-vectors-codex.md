# Codex review: M0 WP vectors (round 1)

Verdict: **Request changes** — two Major issues undermine the fixtures as a Swift source of truth.

- **Major — `backend/app/services/quicklog.py:100–102`: Python range checks do not reproduce JavaScript bound rounding.** Question bounds can be integers beyond JavaScript’s safe range. For a valid double question with `max=9007199254740995` and `last=9007199254740996`, Python returns `""`. JavaScript parses that maximum as `9007199254740996`, accepts the last value, and returns `"9007199254740996"`. The parity vectors only use small bounds, so the current tests pass despite this divergence. **Fix:** convert question bounds to IEEE-754 doubles before comparisons, matching the JSON values received by TypeScript. Add parity vectors with integer bounds around ±2⁵³, covering both minimum and maximum rounding.

- **Major — `backend/tests/test_api_fixtures.py:129–134`: normalization silently erases timestamp contract changes.** Every string under a timestamp key becomes the same valid UTC timestamp without validating the original. A regression emitting a naive datetime, a date-only string, or malformed text would still pass the drift check and supply Swift with a valid-looking fixture. Replacing deterministic interval `due_since` and `next_due_at` also hides actual scheduling changes and produces misleading relationships between fields. The recursive key matching applies inside arbitrary metadata too. **Fix:** freeze the application and database clocks for the scenario and preserve serialized timestamp values, particularly computed due timestamps. Where normalization remains necessary, restrict it to known response paths and validate the original timestamp’s format and timezone before replacing its value. Preserve explicit examples with and without fractional seconds.

Validation: the 18 due/quick-log tests pass; Ruff lint/format and mypy pass for the five added Python files. The DST grid calls the real scheduling implementation and covers actual transitions. Drift comparisons rebuild outputs rather than comparing fixtures to themselves, and the Vitest parity test is included by the existing test pattern. API integration and frontend execution were not verified in this read-only environment.
