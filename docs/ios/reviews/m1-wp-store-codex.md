# Codex review: M1 WP STORE (round 1)

**REQUEST CHANGES**

Reviewed committed HEAD `af0d4e1`, excluding merged C1 changes. An uncommitted `Overlay.swift` edit appeared during review; findings below refer to HEAD.

1. **Blocker — Reset completion can advance an unretired generation.** `ios/QuickrKit/Sources/QuickrData/Store/Registry.swift:135`, called from `StorePartitions.swift:87`. Completion checks only whether *some* `pending_gen` exists. Process A can inspect retired g1 and pause; B completes g1→g2; the app persists a new g2→g3 intent; A resumes and completes that newer intent without g2’s leases, outbox recheck, or retirement. Unsynced g2 writes become stranded, and g2 becomes eligible for deletion. **Fix:** pass the inspected old generation and expected pending generation into completion, compare both inside the registry transaction, and restart recovery on mismatch. Fence intent cancellation similarly. Add a deterministic interleaving test covering consecutive resets.

2. **Major — Lease checks use time sampled before acquiring the transaction.** `Store/Leases.swift:164`, `:202`; `Store/LocalStore.swift:49`, `:59`. A renewal, ack, or retirement queued just before expiry can wait behind another writer and then validate using its earlier timestamp. Renewal can revive an already-expired lease; ack/reset can accept an expired holder. A suspended task can make the gap arbitrarily large. This violates §5.3 validity and the sender fence. **Fix:** capture the `Sendable` clock and call `now()` inside each write closure, after `BEGIN IMMEDIATE` has acquired the lock. Test with a blocked writer and advance the fake clock across expiry before unblocking.

3. **Major — Cancellation/error while acquiring flush leaks the sync lease.** `Store/Leases.swift:192`. Once sync is acquired, only a normal `nil` result releases it. Cancellation during polling, suspension errors, or SQLite errors escape through `try await acquire(.flush, …)` without cleanup. Sync remains owned until its 60-second expiry, unnecessarily blocking rebuild/reset and violating the helper’s acquisition lifecycle. **Fix:** catch every throwing exit after acquiring sync, release sync through cancellation-independent cleanup, and rethrow. Add cancellation and injected-write-error tests asserting immediate release.

4. **Major — Failed-create exclusion is conditional on absence of a server row.** `Store/Overlay.swift:60`. The early `guard server == nil` bypasses `createFailed = true`. Consequently, an unresolved failed create alongside a server row is flagged failed but counted in topic/version totals and eligible for latest-entry selection. §3.2–§3.3 explicitly exclude entities whose create is failed. **Fix:** derive failed-create exclusion independently of content selection; retain server content where appropriate. Add a server-row-plus-failed-create case through both the pure overlay and derived-count repositories.

5. **Minor — The advertised overlay matrix is incomplete.** `Tests/QuickrDataTests/Store/OverlayTests.swift:46`. Tests sample states rather than covering the requested combinations: uncertain/in-flight updates and deletes, cancellation deletes, failed creates with server rows, and `deleted_elsewhere` with existing server content are absent. **Fix:** parameterize active states and add explicit failed/server-presence combinations, checking visibility, error state, counted status, version counts, and latest-entry behavior.

The custom migrator’s bookkeeping matches the checked-out GRDB implementation: both use `grdb_migrations(identifier TEXT NOT NULL PRIMARY KEY)` and identifier-set lookup. I found no concrete later-`DatabaseMigrator` compatibility defect. Persistent WAL, busy timeout, post-commit notification handling, and full-width Mach time conversion are implemented. Suspension observation is enabled, but lifecycle posting of suspend/resume notifications is not wired in this diff, so 0xDEAD10CC protection remains an integration obligation.
