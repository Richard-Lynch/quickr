# Codex review: M1 WP B7 (round 1)

**REQUEST CHANGES**

1. **P1 — “More…” extends the shared protocol without updating its authority.** `backend/app/services/notification.py:184` emits `kind="open"` and `k=m`, but notifications.md §4.2 permits only `o/n/i`, and §4.3 hashes only `log/input`. §2.3 authorizes the foreground action’s behavior, so the implementation choice is reasonable; its encoding remains unspecified. A conforming Swift implementation can reject it or produce a different category hash. **Fix:** amend §4.1–4.3 to define `open`, `m`, the empty value, foreground registration and handler behavior; explicitly exempt More from the blanket “No `.foreground`” rule.

2. **P1 — Number formatting is not sufficiently specified for independent Swift reproduction.** `backend/app/services/notification.py:137` rounds `Decimal(repr(float(x)))`, introducing a shortest-decimal conversion before rounding. The authoritative §4.4 merely says half away from zero: rounding binary64 `2.675` directly can yield `2.67`, whereas this implementation yields `2.68`, changing identifiers and hashes. Fixture prose describes the extra step but does not fully define shortest-representation tie selection. **Fix:** normatively specify binary64 conversion, shortest-decimal selection/ties, rounding and negative-zero handling; add cross-language vectors for midpoint neighbors, subnormals and extreme magnitudes.

3. **P2 — `last_value` rejects answers the current question accepts.** `backend/app/services/notification.py:119` nulls values exceeding `decimals`, while `backend/app/services/answers.py:65` validates doubles using finiteness and bounds only. Thus `7.25` remains a valid answer with `decimals=1`, yet loses its repeat action, contrary to §2.3. The tests and vectors cement this additional rule. **Fix:** settle the contract explicitly. Either enforce decimal precision consistently in answer validation, or retain valid historical values and specify a display/identifier representation that logs their exact value rather than a rounded replacement.

4. **P2 — Added N+1 reads can prevent slot-progress delivery from advancing.** `backend/app/services/scheduler.py:120–133` batches versions but then awaits one history query per eligible topic, including enums with ≤4 options whose counts cannot affect output. These queries run after the delivery deadline starts and before any send. With enough due topics/history, preparation can exhaust every tick’s budget; B6’s progress ledger cannot help because no target finishes. **Fix:** batch ranking/latest-answer reads, skip unnecessary counts, and bound preparation or process due topics incrementally. Add a regression proving progress under expensive preparation.

Ranking otherwise correctly scopes counts by topic/key, excludes multi-select answers, ignores inactive options during selection, and resolves ties by option order. NFC normalization, UTF-8 hashing and scalar truncation match the stated rules. APNs headers/rendering and Web Push’s original field values/order appear preserved.

The size test includes maximum slugs and units, but four-byte emoji are not the serialization worst case: permitted control characters escape to six bytes. Add escaped-character coverage. Generated vectors are deterministic snapshots, but need independent Swift verification. Tests were inspected, not executed.
