# Codex review: M1 WP VAL (round 1)

**REQUEST CHANGES**

1. **P1 — Repeat-last can silently change the previous answer.** [RepeatLast.swift:12](/Users/richie/code/quickr-worktrees/ios-m1-val/ios/QuickrKit/Sources/QuickrCore/Validation/RepeatLast.swift:12) converts stored answers through form inputs before deciding whether they still validate. A previous multi-select `["a","b"]` becoming single-select silently logs `"a"`; a string `"12"` becoming numeric silently logs `12`. The server rejects those original values against the new types. PLAN §2 says invalid previous answers should open the prefilled record screen. **Fix:** validate stored value shapes before automatic repeat; reserve coercion and lossy conversion for the prefill path. Also allow an empty answer map when it validates—all-optional topics can have valid entries without answers.

2. **P2 — Swift accepts strings the server subsequently rejects.** [AnswerValidator.swift:65](/Users/richie/code/quickr-worktrees/ios-m1-val/ios/QuickrKit/Sources/QuickrCore/Validation/AnswerValidator.swift:65) checks lengths after JavaScript trimming, whereas `services/answers.py::_normalise` uses Python `strip()`. For a required string, `"\u{0085}"` passes Swift but becomes unanswered on the server; with `min_length=2`, `"a\u{0085}"` passes Swift and becomes a one-character server value. U+001C–U+001F produce similar discrepancies. **Fix:** validate the server-normalized string before returning success, and add cross-language whitespace vectors. Preserve JavaScript trimming separately where frontend parity requires it.

3. **P2 — String validation and messages disagree with the frontend for supplementary characters.** [AnswerValidator.swift:65–72](/Users/richie/code/quickr-worktrees/ios-m1-val/ios/QuickrKit/Sources/QuickrCore/Validation/AnswerValidator.swift:65) counts Unicode scalars; `answerSchema.ts` uses UTF-16 `value.length`. With `min_length=2`, `"😀"` fails Swift with `At least 2 characters (1 so far)` but passes the frontend. With `max_length=1`, Swift/server accept it while the frontend rejects it. This intentionally matches Python, but violates the claimed frontend acceptance and exact-message parity. **Fix:** reconcile the frontend to code-point counting, retain server-compatible Swift counting, and add shared emoji/message tests.
